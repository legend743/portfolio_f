Who am I ?

A Backend Developer Who Cares About Systems That Don't Fall Over

Hi, I'm Mohd Faisal — a backend developer who started out in QA, which means I care as much about why something breaks as I do about building it in the first place. My primary work is in .NET, building and maintaining REST APIs for production systems, including an ERP platform for a US-based client. I also work in Java/Spring Boot on the side, most recently building and hosting a hospital management platform end-to-end. Lately I've been especially interested in reliability and resilience — I'm currently building a desktop POS application (iPOS-Client) with a custom server discovery module that automatically promotes a new host through leader election if the active server goes down. That mix of hands-on QA instincts and backend engineering is what I bring to every project: code that works, and keeps working.

My Services

API Development

Your application is only as reliable as the APIs behind it. I build REST APIs in .NET — secure, well-documented (Swagger/OpenAPI, JWT authentication), and designed to stay up. My work includes ProcurementPortal, an ERP platform for a US-based client, and iPOS-Client, a POS system with a custom failover module that automatically recovers if a server goes down. If uptime and clean integration matter to your project, this is where I focus.

Manual Testing Services

Bugs are cheaper to catch before launch than after. I bring hands-on QA experience across both software and hardware — from functional and UI testing to specialized work like voltage/stress testing and OTA (Over-the-Air) command verification on hardware devices. That background means I don't just test whether a feature works — I test what happens when things go wrong, which is exactly what protects your product in production.

Api FunctionalTesting Services

Before your APIs reach real users, I make sure they behave correctly under real conditions. I validate endpoints, HTTP methods, and request/response integrity to catch functional issues and edge cases early — so integration problems get found in testing, not in your client's inbox.
